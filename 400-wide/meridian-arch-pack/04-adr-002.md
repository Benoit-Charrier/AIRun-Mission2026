# ADR-002: Use Kafka with the Outbox Pattern for Cross-Service Event Publishing

## Context

Meridian Phase 1 has three services (Cart, Checkout, SAP CDC consumer) that must publish events reliably to the Order Event Bus (Kafka) while also persisting state to PostgreSQL. Without a coordination mechanism, a service can commit to the database and then crash before publishing to Kafka — or publish to Kafka and then fail to commit — leaving the inventory read cache and downstream order processors in an inconsistent state. The junior MRG team has limited distributed-systems experience; the solution must be operable without deep Kafka expertise at the application layer.

## Decision

We will use the Outbox pattern: Cart Service and Checkout Service write domain events to an `outbox` table in the same PostgreSQL transaction as their domain state change. A CDC connector (Debezium) tails the PostgreSQL WAL, reads committed outbox rows, and publishes them to the appropriate Kafka topic. The `outbox` table is the only permitted Kafka write path for these services — services MUST NOT call the Kafka producer SDK directly from application code.

## Alternatives Considered

1. **Direct synchronous Kafka producer calls from application code** — rejected because dual-write (write to DB + write to Kafka in the same request without a transaction) creates a split-brain window: a crash between the two writes leaves the database committed but Kafka unpublished (or vice versa), causing permanent inventory-cache staleness that would inflate the phantom-stock cancellation rate — the exact KPI Meridian is trying to fix.

2. **Saga choreography with compensating transactions instead of Kafka events** — rejected because Saga requires each participating service to implement compensating logic; for a junior team on a 18-month timeline this adds a coordination surface that is error-prone to implement and hard to debug. The Outbox + Debezium pattern keeps event reliability at the infrastructure layer, not the application layer.

## Consequences

- **Positive:** Event publishing is exactly-once relative to the database transaction — no dual-write split-brain. Application code is simpler: services only interact with PostgreSQL, not with Kafka.
- **Negative:** Debezium (CDC connector) is an additional operational component that must be monitored for consumer lag and replication slot health on PostgreSQL. If the replication slot grows without bound (e.g. Debezium is down for > 24h), PostgreSQL WAL retention can fill disk — an explicit PagerDuty alert on replication slot lag is required before launch.

## Agent-Readable Summary

Cart Service and Checkout Service MUST publish Kafka events via the Outbox pattern (write to `outbox` table in the same PostgreSQL transaction; Debezium CDC connector reads and forwards). Do not add direct Kafka producer SDK calls inside application service code. Any new service that needs to publish to the Order Event Bus must follow the same Outbox pattern — do not introduce a new publication mechanism without an ADR revision.
